二、	研究計畫內容：

(一)	研究動機與研究問題
研究動機
	在真實SOC維運情境中，告警量龐大且常伴隨誤報與重複告警，容易造成alert fatigue，使分析師人工triage(初步分流/研判)成本上升並有漏判風險[1] (Abstract處)。因此需要在不大幅改變既有流程下，對alert/incident的可行動性（actionability，是否真的需要分析師處置）與優先級進行排序，以提升triage之效率[2] (Abstract處)。同時，真實日誌在不同設備/批次/類型下常出現欄位缺漏、格式差異、時間戳記不一致等問題，若前處理不穩定，後續關聯/排序結果會直接被資料品質影響[4](Sec 2.3.1處)。且單筆系統日誌屬於event而不一定為需回報的資安事件 (incident)，是否回報須依事件之間的關聯與影響等做判斷[3]。
	因此本研究選用常見且重要的系統日誌來源之一，防火牆日誌[4](Sec 2.1.1處)，作為初步資料來源，在缺乏incident標註且資料品質可能不統一的情形下，探討如何降低分析師之人力並提升triage效率，並在使用LLM協助時不透漏敏感資訊，不增加錯誤率。
研究問題
 	現業界SIEM多以規則/查詢式關聯把多筆events聚合為告警/案件，如FortiSIEM 可用correlation rule設定條件，一定數量event(s)符合後才聚合成incident，Elastic以alert suppression依欄位分組並在時間窗內合併重複輸出。
然而學界指出這類規則式關聯主要依賴專家事先把可疑事件組合/順序寫成規則，故只能抓到已知且已被規則描述的模式，若攻擊行為換了順序，用不同欄位呈現，或出現新的事件組合，系統往往無法自動把這些脈絡相近的事件串成同一條事件鏈。
	並且因SOC實務已採固定的triage與回報流程（以案件清單分流、逐案調查與回報），若要求分析師改用全新的操作流程和大量手動標註，將提高導入成本並降低實務可行性。
故本研究欲在不大幅改變既有工作流的前提下，引入能在未/少量標註事件上學習序列關聯的DeepCASE與以actionability做優先排序的TEQ的ML方法，探討如何在真實場域(未/少量標註事件)下提升事件關聯聚合與triage成效。
(二)	研究方法及步驟
研究方法
本研究以高市府的資料集為主，公開資料集為輔，將日誌中的大量events以ML方法聚合成易審查的incidents，依嚴重程度排序，優先處置較嚴重者，並引入去重/節流機制以降低同一情境反覆觸發造成的重複告警。接著將結果與無使用ML之業界流程做成效對比。
	再透過本地端LLM產生精簡回報與處置建議，將incidents分析結果輸出成易讀、可支援處置決策的分析報告和朔源圖，降低人工分析之負擔。完成後把整體流程整合至網頁呈現，模擬商業化自動流軟體的運作。
研究步驟


1.	資料解析與正規化
讀入防火牆事件資料，此處以高市府計畫提供之PAN-OS log為主，公開資料集(如AIT Log Data Set v2.0)為輔。AIT Log Data Set v2.0提供多種格式之日誌與對應事件之標籤（攻擊名稱和行號，未標註視為normal），可用於驗證跨格式的log處理/正規化流程，並在公開資料上直接計算Top-K命中率與誤報等指標。
 	從Raw Event Log等中取出後續會用到的欄位（如type/subtype、src/dst、rule、action、severity、threat id/name、app、port等），並整理成一致格式（欄位命名、型態、缺值處理、時間欄位一致）。
後續可再擴張至處理其餘網路安全設備日誌格式(IDS/Proxy/Flow等)之資料。
2.	（Baseline）不使用ML的incident化＋去重:以時間窗＋欄位key把events聚成incident candidates（例如同src/dst/rule/threat在某時間窗內視為同incident）。
再以去重/節流在時間窗內合併重複回報，同key只輸出一次，其餘命中則只更新count/last_seen等統計。
3.	(ML) DeepCASE事件序列關聯/分群 → incident instances: 先定義事件序列的建立方式（以哪個實體建立序列、回看長度、回看時間上限），把日誌事件轉成可餵給模型的序列表示。
使用DeepCASE進行事件序列之關聯分析與分群，得到脈絡相近的事件群（cluster）。
	再用sessionization針對每個cluster，把同一序列主體下的events依時間排序，當相鄰事件時間間隔超過max_gap時即切段成不同session，每個session視為一個可回報的 incident instance，避免把同一cluster中間隔太久的不同時間段發生的事件們誤併。
4.	incident-level去重/節流（含state-aware）: 在incident instances層級做去重/合併，並將deduplication key與時間範圍視為設計變因進行比較。
	加入state-aware更新策略：同情境重複出現只做更新，不重覆回報，但在嚴重度或影響範圍明顯提升時，新增一筆升級回報。
5.	That Escalated Quickly (TEQ) :可行動性/優先級排序 : TEQ在不大改既有流程下，對alert/incident預測可行動性（actionability，是否真的需要分析師處置，分數越高越需要），並用priority分數做優先級排序，讓分析師先看最可能需要處置的案件，同時把大量低價值告警往後移或直接抑制。
	基於此，本研究在完成incident聚合與去重後，會對每個incident建立incident-level特徵，以少量人工抽樣標註actionability來訓練一個輸出priority分數的模型，並用該分數排序，再依事件嚴重度判斷是否需回報和回報等級(使用如CISA severity分級概念)。
6.	成效評估（Baseline vs. ML）: 使用 SOC 流程中注重之量化指標進行評估，對比在 SOC 流程中加入/不加入本研究採用的機器學習方法何者有較好的成效：
降低工作量/所需時間、誤報率(被回報但其實不需人工處理之incidents的比例)
提升告警縮減率（=events/incidents）、重複告警抑制成效（duplicate suppression = (incidents_before–incident_after) / incidents_before )、Top-K命中率（例每天只看前K個，看其中真正為嚴重事件需要被處置的比例）
比較Baseline（規則式）vs. 加入ML（DeepCASE＋TEQ）在相同資料上的差異。
7.	溯源圖（事件關聯圖）建立 : 第一版以一般資料庫儲存incidents與其entities統計，後端輸出JSON產生單一incident的關聯圖。對每個incident產生一張entity關聯圖（節點為src/dst/rule/threat/app等，邊為count/first_seen/last_seen等），events以時間線/證據列表輔助呈現，再提供總覽層的incidents清單（依 priority 排序），仿照業界流程。
	如需要做跨incidents的多跳關聯追查和互動式展開（輸入/點選某IP即時展開 1–2層關聯、找共同dst/threat/rule、追查一段期間的關聯鏈）時，才動態新增Neo4j將全域entity–entity關係存成圖，透過圖查詢直接取回子圖供前端呈現。
8.	本地 LLM 回報 : 本研究採用文獻[7]之RAG（hybrid retrieval）流程：
	先由incident內可用的入侵指標(IOC)（如外部IP／domain／URL）對外部CTI平台API進行結構化查詢（如VirusTotal平台）取得相關情資，若無可用之外部IOC，則略過此步。
	再以incident摘要與threat資訊對本地CTI向量資料庫做相似度檢索，擷取相關之CTI資訊。(本地CTI資料庫先使用像ATT&CK建立MVP。) 
	最後以incident證據和上述兩樣檢索結果，並確認在敏感資訊皆去除後，依固定格式作為本地LLM輸入，輸出精簡摘要/風險/建議處置/需人工確認項目等，再以定義好之規則檢查與人工抽查，驗證回報品質。
9.	整合至網頁介面（前後端分離）
前端: React + typescript。前端以目前主流/常見之架構做撰寫。先做incidents清單頁（排序、篩選、Top-K），以及單一incident詳細資訊頁（entity 圖、事件時間線、回報區）。
使用清單triage加單incident調查介面，與業界 SIEM 的 Incident Review/調查頁呈現方式一致。
後端: API。定義資料結構與API規格（events/incident list/incident detail/graph/report）。後端以API形式提供events上傳/查詢、incidents清單與單incident細節、關聯圖與回報內容等服務，並負責執行資料解析正規化與ML聚合/排序流程。
讓使用者能輸入events資料，處理後在網頁上及時查看結果。
(三)	預期結果
在模擬業界網路安全設備系統日誌的處理流程的基礎下，融入機器學習方法DeepCASE與TEQ研究，期望在真實場域的防火牆等日誌中能取得較好的量化表現，建立完整的自動化流程並朝商業化軟體邁進。
